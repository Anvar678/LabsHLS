# Стенд курса «Технологии обработки больших данных»

Файлы запуска сервисов стенда: объектное хранилище, каталог таблиц Iceberg,
движки запросов, аналитическое хранилище, брокер, оркестратор, потоковый
движок и инструмент визуализации — по профилям лабораторных работ и по
вариантам. Требования к машине стенда, порядок работ и справочник по сервисам —
в методических указаниях курса.

Репозиторий клонируется на машину стенда, и клон становится рабочим
репозиторием студента: сборщик данных, запросы, конвейеры и подключения
студент пишет в нём же, рядом с готовыми файлами.

## Первый запуск

Нужны Docker Engine и Compose не ниже 2.20; проверены версии 2.20.3, 2.24.6
(пакет `docker-compose-v2` Ubuntu 24.04) и 5.3.1. Машина стенда — виртуальная
машина или дистрибутив WSL2 по разделу «Стенд курса» методических указаний.

```sh
git clone https://github.com/nitwof/bigdata-stand ~/stand
cd ~/stand
git config user.name "Фамилия Имя"      # автор коммитов; без него git pull
git config user.email <адрес>           # с исправлением стенда не сливает
cp .env.example .env                    # значения — задание работы 1
docker compose run --rm stand-init      # каталоги данных под сервисы (один раз)
docker compose build collector          # оболочка службы сборщика
```

Если Docker Hub отвечает на загрузку образа ошибкой 429, движку задаётся
зеркало реестра — тот же раздел методических указаний, «Docker Engine».

Сеть виртуальной машины — NAT гипервизора, в котором машина видна рабочей
машине, или сеть «только узел». Режим «сетевой мост» не используется: сервисы
стенда работают без паролей, и в этом режиме их порты открыты всей сети.

Службу сборщика поднимает `docker compose --profile lab1 up -d`, когда
программа сборщика написана: без `collector/src/main.py` оболочка завершается
с кодом 78 и перезапускается.

Каталог `data/` создаёт одноразовый сервис `stand-init`; в репозиторий он не
попадает. Сам `data/` принадлежит пользователю с uid 1000, подкаталоги —
пользователям своих сервисов, поэтому полный сброс стенда (удаление `data/`)
делается с правами администратора. Остальное стенд готовит сам при первом
запуске нужного профиля: bucket озера — профиль работы 3, склад каталога
таблиц — профиль работы 4. Эти шаги повторяются при каждом `up` и ничего не
портят. Образы сервисов из `services/` собираются первым `up` нужного
профиля; сеть нужна только при сборке.

Порты по умолчанию — штатные порты стенда, перечень — в `.env.example`. Если
порт на рабочей машине занят, переопределяется переменная `PORT_*`.

## Как это устроено

Состав запущенного задают три вещи:

1. **Вариант** — набор файлов в `COMPOSE_FILE` (переменная в `.env`): базовый
   `compose.yaml` и по одному файлу на ось — `compose.s3-*.yaml`,
   `compose.engine-*.yaml`, `compose.bi-*.yaml`, `compose.broker-*.yaml`,
   `compose.orchestrator-*.yaml`, `compose.stream-*.yaml`. В работе 1 в
   `COMPOSE_FILE` только `compose.yaml`; работа, которая фиксирует ось,
   дописывает в конец файл своего значения. Два файла одной оси Compose не
   отвергает, а сливает в один сервис с чужими настройками.
2. **Работа** — профиль: `docker compose --profile lab4 up -d` поднимает
   сервисы, нужные заданию работы 4, и постоянно работающие.
3. **Параметры варианта** — остальные переменные `.env`: адреса, учётные
   данные, значения осей, фильтр источника и предел слоя сырых данных.
   Сборщику, `spark`, `duckdb` и потоковому заданию Spark виден весь `.env`;
   движку `engine` и оркестратору — только переменные `S3_*`, `CATALOG_*` и
   `WAREHOUSE_*`, поэтому правка остальных строк их не перезапускает.

Имена сервисов — роли, а не продукты: текст работы одинаков для всех
вариантов. Порт роли одинаков у всех вариантов и в течение семестра не
меняется.

## Сервисы и роли

| Роль | Продукт | Порт | Профили |
|---|---|---|---|
| `collector` | программа студента в оболочке | 9101 (счётчики) | всегда |
| `s3` | SeaweedFS или Garage | 9000 (API), 9001 (интерфейс SeaweedFS; у Garage — административный API) | lab3–lab9 |
| `catalog` | Lakekeeper + PostgreSQL | 8181 | lab4–lab9 |
| `engine` | Trino, StarRocks или встраиваемый DuckDB | 8080 (интерфейс и SQL у Trino), 9030 (SQL у StarRocks); у DuckDB портов нет | lab4, lab5, lab7, lab9 |
| `warehouse` | ClickHouse | 8123 (HTTP), 9002 (родной) | lab5, lab7, lab8, lab9 |
| `broker` | Kafka или Redpanda | 9092: изнутри стенда — `broker:9092`, программам на стенде вне контейнеров — `localhost:9092` | lab6, lab8 |
| `registry` | Karapace; у Redpanda реестр встроен, `registry` — сетевой псевдоним брокера | 8081 | lab6, lab8 |
| `bi` | Metabase, Superset или DataLens | 8088 | lab5, lab8, lab9 |
| `orchestrator` | Airflow или Dagster | 8082 | lab7 |
| `stream` | Flink или потоковое задание Spark | 8083 | lab8 |
| `spark` | Spark с Iceberg — запись и обслуживание таблиц | 4040 (интерфейс задания, пока задание идёт) | по требованию |
| `duckdb` | встраиваемый движок для работ 2–3 | — | по требованию |

Брокер объявляет клиентам адрес `localhost`, поэтому клиенты брокера
запускаются на стенде.

Сервисы `spark` и `duckdb` не работают постоянно: они запускаются командами
`docker compose run --rm --service-ports spark …` и
`docker compose run --rm duckdb`. Потоковое задание Spark (`stream` у
варианта `spark-ss`) работает в фоне до остановки:
`docker compose run -d --name stream-job --service-ports stream …`. У `up`
профиля работы 8 контейнер `stream` без команды сразу завершается и порт не
занимает. `docker compose down` контейнер `stream-job` не останавливает: он
удаляется командой `docker rm -f stream-job`.

Запросы и задания (`jobs/`) видны сервисам `spark`, `stream` и
`orchestrator` как `/opt/jobs` (только чтение), конвейеры (`dags/`) —
оркестратору, тоже только на чтение. У оркестратора `/opt/jobs` — в пути
поиска модулей Python. Airflow перечитывает `dags/` раз в 30 с. Оркестратор
выполняет по одной задаче (Airflow) или по одному запуску (Dagster): у каждого
шага Spark своя JVM, и повторный счёт за несколько суток иначе не помещается
в предел памяти.

Режим службы сборщика задаёт `COLLECTOR_MODE` в `.env`: `record` с работы 1,
`produce` с работы 6. Разовые режимы (`backfill`, `replay`) запускаются
командой `docker compose run --rm collector <режим>`: аргумент перекрывает
значение из `.env`.

Вход в веб-интерфейсы:

- Airflow — без пароля; новый DAG появляется выключенным, и ни расписание, ни
  повторный счёт не запускаются до `airflow dags unpause`;
- Superset — `student` / `student`;
- DataLens — `admin` / `student`;
- Metabase — учётная запись создаётся при первом входе.

## Что пишет студент

Стенд даёт сервисы, но не связи между ними и не код обработки данных. В
рабочем репозитории студент пишет:

| Путь | Что там |
|---|---|
| `collector/src/`, `collector/requirements.txt` | программа сборщика данных и её зависимости |
| `schemas/` | схема события |
| `jobs/` | запросы и задания движков |
| `dags/` | конвейер оркестратора |
| `conf/trino/`, `conf/spark/` | подключения Trino и Spark к каталогу таблиц и хранилищу |
| `SOURCE.md`, `CATALOG.md`, `NOTES.md` | паспорт источника, каталог данных, журнал работ |

Учётные данные стенда живут в `.env` и в репозиторий не попадают: файлы
подключений ссылаются на них как `${ENV:ИМЯ}`.

## Исправления стенда

Готовые файлы стенда не правятся. Исправление стенда в течение семестра
приходит в этот репозиторий и забирается в рабочий репозиторий:

```sh
git pull --no-rebase --no-edit                 # слияние с исправлением
docker compose --profile labN up -d --build    # N — текущая работа
```

Случайно изменённый готовый файл возвращается командой
`git checkout -- <файл>`.

## Остановка

`docker compose down` без профиля останавливает только сервисы без профиля.
Стенд целиком останавливается перечислением всех профилей:

```sh
docker compose --profile lab1 --profile lab2 --profile lab3 --profile lab4 \
  --profile lab5 --profile lab6 --profile lab7 --profile lab8 --profile lab9 \
  --profile tools down
```
